### Diff-scope review (bmad-review: adversarial, edge-case, verification-gap)

Review scope: `e4088af^..46107c8`, weighted toward story boundaries: server versioning and idempotency (3.2) against the client retry and refetch (3.3), domain `is_best` (3.1) against the table, filter and counts (3.4), and the LocationsTable refactor (3.4) against the epic 2 Locations step. All three lenses finished. Each finding below was re-checked against HEAD.

**R1. Behind the Next.js `/api` rewrite, an unreachable backend returns 500, so the AD-12 retry path never runs** (verification-gap; re-checked live). Severity high.
- The client counts only a thrown fetch or 502/503/504 as transient (`frontend/lib/commands/client.ts:30`, `:137-140`). Any 500 goes to `fail()` (`:160`).
- The browser only calls `/api/*`, which `frontend/next.config.ts:6` rewrites to FastAPI (AD-2). When the proxy fails, Next answers `500 Internal Server Error` (`node_modules/next/dist/server/lib/router-utils/proxy-request.js`, `onProxyError`: `res.statusCode = 500`). The CI-fix spec already found the same behaviour for its 30 s `proxyTimeout` (`spec-ci-44979957249-…md:32,67`).
- **Live check:** with `next dev` and the backend stopped, `POST /api/plans/{id}/commands` returned `500 Internal Server Error`, and Next logged "Failed to proxy … ECONNREFUSED".
- **Result:** locally, and on the AD-2 fallback deployment (a Next rewrite to the backend URL), a backend restart never triggers "The last change was not saved yet. Trying again." The change is dropped at once with "The change was not saved." The retry tests (`frontend/tests/commands.test.tsx`) feed fake statuses to a stubbed fetch, so nothing exercises the real rewrite. How the Vercel Services rewrite behaves is not verified.
- This is a 3.3/AD-2 boundary that no single story saw.

Disposition: **fix now**.

**R2. The version-consistent refetch can get stuck on an old set** (adversarial + edge-case). Severity medium.
- `refetchConsistent` re-fetches only queries whose version is below the confirmed version (`client.ts:177-189`). If another writer commits in between, so that summary returns N+2 and locations N+1, nothing counts as stale. `useConsistentPlanData` then keeps the previous set (`react.tsx:85-94`), and the user sees the toast and "Saved automatically" next to the old marks.
- On first load, the Best locations step (`best-locations-page.tsx:239-260`) shows `PlanOpening` until summary and locations agree. If a write lands between the two GETs, nothing re-fetches unless this client sends a command, or a window-focus refetch happens.
- Both need a second writer (another tab). In M1 there is one user, but the 3.3 triage rejected the related "below confirmed version" note for that reason, and it was never tested.

Disposition: **fix now**. Bring the rule up to the highest version seen, and give the first load a bounded refetch.

**R3. If `crypto.randomUUID()` throws, the plan stays "Saving…" forever** (adversarial + edge-case). Severity medium.
- `send` sets `pending: true` (`client.ts:104`), but builds the command, including `this.randomId()`, before the `try` (`:105-110`). So a throw skips the `finally` that clears `pending`.
- `crypto.randomUUID` exists only in secure contexts. Opening the dev server by LAN IP over HTTP makes every plan-changing control stay `aria-disabled` until reload.
- The 3.3 triage rejected the missing fallback ("localhost and HTTPS only"), but did not see that the throw also leaves `pending` stuck.

Disposition: **fix now**. Build the command inside the `try`, and add a fallback.

**R4. Real write contention becomes a 500 that is not retried, and the server's re-read loop cannot be reached** (adversarial + edge-case). Severity medium.
- `BEGIN IMMEDIATE` on SQLite and `FOR UPDATE` on Postgres lock the row before the read (`backend/swp/store/db.py:47-58`, `store/plans.py:145-151`). So the conditional UPDATE never sees 0 rows outside the monkeypatched test, and the retry loop in `run_command` (`app/commands.py:36-57`) is dead code in practice.
- A lock wait longer than pysqlite's 5 s busy timeout raises `OperationalError`, which becomes a 500. The client then drops it without a retry (R1 path). The 3.2 triage rejected retrying driver errors as "not met in practice". The lock scope includes parsing the full import (A5).
- **Live check:** 10 concurrent commands on `data/sample/` all applied, with versions 7-16 in 0.06-0.34 s. So this is a load-dependent risk, not an observed failure.

Disposition: **fix now** (cheap). Retry or map lock errors to 503, and read only id/version/state under the lock.

**R5. Idempotency is tested on each side, but never across the boundary** (verification-gap). Severity medium.
- The server test posts the same body twice (`backend/tests/app/test_commands.py`). The client test checks that retried bodies are identical, using an injected id. The Playwright journey (`frontend/e2e/best-locations.spec.ts`) covers only the happy path.
- The case AD-6/AD-12 exist for (applied on the server, response lost, client retries) is never tested end to end.
- **Live check:** a repeated `command_id` returned the stored `{version:2, events:[mark_set]}` with no version bump.

Disposition: **fix now**. Add a Playwright test that lets the first POST through and replaces its response with a 503.

**R6. The toast fires on a confirmed no-op** (adversarial). Severity low.
- `sendMarkChange` toasts on any `"confirmed"` outcome (`best-locations-page.tsx:77-85`), and a no-op confirms with `events: []`. The UI disables already-marked buttons, so this is reachable only through a race, such as a mark set from another tab. It matters in Epic 5, when the toast gains a count and a **View** action.

Disposition: **fix now** (one line, with the Epic 5 toast in mind).

**R7. Smaller items.** Disposition: **defer** for all.
- **"Saved automatically" after a failed refetch:** `saved: true` is set even if the refetch failed, because `invalidateQueries` does not throw (`client.ts:119-121`). `fail()` waits for its refetch before it shows the notice (`:153-156`).
- **Mark on rows that are already best:** Single location mode shows **Mark** on rows already best through an aisle or level mark (`best-locations-page.tsx:128-151`). The 3.4 triage rejected this, since UX-DR28 asks for Mark/Unmark on every row.
- **Reused `command_id`:** a reused `command_id` with another body returns the old result (`app/commands.py:23-28`). The 3.2 triage rejected this.
- **Stored results and later event changes:** stored results are re-validated against today's event union (`app/commands.py:27`). Upcast them when an event shape changes.
- **Other 5xx and "not saved" for saved changes:**
  - A 5xx other than 500/502/503/504 takes the toast path.
  - An unreadable 2xx is reported as "not saved" although the server committed it (`client.ts:141-148`).
  - Retries exhausted after a commit also say "not saved".
- **No POST timeout** (`client.ts:132-136`). The 3.3 triage rejected this.
- **Filter updaters:** the shared LocationsTable spreads the render-time `filters` instead of using functional updaters (`locations-table.tsx:171,186,192`). No user-visible effect.
- **Flow bar and page body:** the flow bar reads the summary directly while the page renders only consistent sets (`toolbar.tsx:24-26`), so they can briefly disagree.
- **Coverage computed twice:** coverage is computed twice per locations row (`views/locations.py:85-89`).
- **Missing tests:** no test covers the primary Mark button being disabled while saving (`best-locations-page.tsx:184`), or the page's version-consistent pairing (`:242`).

**Story 3.4 against epic 2: still open.** The refactor kept the epic 2 Locations behaviour, including the R1 defect from that retro: `locations-page.tsx:42-46` still resets the filters to `{...NO_FILTERS, aisle}` on every URL change. The Best locations step keeps its filters in component state and does not inherit the defect.
