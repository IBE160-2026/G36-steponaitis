## Findings

### Cross-story findings (no single story saw both sides)

- **F1. Busy row lock on login gives 500, not 503, and the public demo makes it reachable.**
  - Where: `backend/swp/app/auth/__init__.py:137` (`login_attempts.reserve`), `backend/swp/store/login_attempts.py:20-45` (`SELECT … FOR UPDATE` on one row, then UPDATE, prune and COMMIT), `backend/swp/store/db.py` (`NullPool`, `lock_timeout` 3 s).
  - Problem: the 16.0 triage #6 deferred this because "transactions are tiny" (`deferred-work.md:2-4`). 16.1 made every store call a new NullPool connection from `iad1` to the Stockholm database. 16.2 published `demo`/`demo`, so all correct logins for `demo` now queue on one hot row. Measured live: a DB-touching request costs about 1 s (Behavior verification).
  - Lens: adversarial, edge-case. Severity raised from 16.0 triage #6.
  - Disposition: **fix** (action item 1).
- **F2. `demo_login` returns 500 when the seed is skipped as busy; the comment says that can't happen.**
  - Where: `backend/swp/app/auth/__init__.py:182-187`. The comment "the seed above always leaves a row" is false since 16.0 added the `UsersBusy` swallow in `seed_demo_account` (`:166-171`).
  - When: exactly after the README upgrade note (16.2) tells the operator to delete the `demo` row.
  - Lens: adversarial, edge-case.
  - Disposition: **fix** (action item 1).
- **F3. Count-before-verify (16.0) meets a published, shared login (16.2).**
  - Where: `auth/__init__.py:137-145`, `domain/accounts.py:108-122` (`after_failure`: "No time window").
  - Problem 1: every login, correct ones too, counts until its own `clear`. Five overlapping `demo` logins in the multi-second live window lock `demo` for 60 s for everyone.
  - Problem 2: an attempt aborted between `reserve` and `clear` (timeout, dropped connection) stays counted with no decay.
  - The 16.0 triage #4 accepted the correct-login lock as needing "≥5 simultaneous logins", which was judged on local timings. The 16.2 triage #14 rejection ("only failed logins count after a success clears") rests on the pre-16.0 model. Its conclusion still holds, because `e2e:public` makes one Log in attempt per run, but its reason does not.
  - Demo version is never throttled (`demo_login` never touches `login_attempts`), so examiners always have a way in.
  - Lens: adversarial, edge-case.
  - Disposition: **defer** with a decision (action item 2).
- **F4. `login_attempts` rows for names that never lock are never pruned.**
  - Where: `backend/swp/store/login_attempts.py:48-63` prunes only rows with `locked_until <= now`. Since 16.0 every attempt writes a row, also for unknown names. Since 16.2 the login is public, with no IP limit (out of scope per epic context).
  - Effect: a username spray grows the table on the free Supabase database.
  - Lens: adversarial, edge-case.
  - Disposition: **defer** (action item 2).
- **F5. Production startup accepts an empty or SQLite `DATABASE_URL`; the custom-SQLite `mkdir` still raises on a read-only disk.**
  - Where: `backend/swp/app/startup.py:60-61` checks only "is it set". `backend/swp/config.py:86-90` has a custom `sqlite:///` branch that calls `mkdir` without the `suppress(OSError)` that `184070b` added to the default branch.
  - Effect: the same class of failure `184070b` fixed (a traceback instead of one refusal line). On `/tmp`, data would vanish between cold starts.
  - The guard must key on `VERCEL`, because `e2e:production` runs SQLite with `APP_ENV=production`.
  - Lens: all three.
  - Disposition: **fix** (action item 3).
- **F6. No automated check of the live deployment beyond `SELECT 1`.**
  - Where: `.github/workflows/keep-alive.yml:19` curls only `/api/health`. `npm run e2e:public` (`frontend/playwright.public.config.ts`) is manual. `startup_problems` never looks at the feature flags.
  - Effect: a dropped `FEATURE_DEMO`/`FEATURE_AUTH` in the Vercel dashboard, or a missing `demo` row, stays green everywhere.
  - Related: removing the `uj5` skip placeholder in `6659a7f` means `npm run trace` counts UJ-5/NFR-5 as covered by runs that never touch the deployment. The live evidence is the session log of 2026-11-28 and goes stale with each push.
  - Lens: verification-gap (findings 1 and 4), adversarial (13).
  - Disposition: **fix** (action item 4).
- **F7. Database round trips from the function region dominate live latency.**
  - Where: the session log `880-*` records the function in `iad1` and Supabase in Stockholm, and a move to `arn1` was abandoned.
  - Measured 2026-11-28:
    - `/api/session` (no DB): 0.21 s
    - `/api/health` (`SELECT 1`): 1.04 s, three times
    - `GET /api/plans` as `demo`: 1.9 s, three times
    - demo login: 1.05 s
  - The live login also needed `52a7fb5` (5 s → 30 s Playwright timeout).
  - NFR-8 ("respond within 1 second") is stated for a typical laptop, so this is not an NFR breach. It is the examiners' experience, though, and it widens the F1/F3 windows.
  - Disposition: **defer** with a decision (action item 5).

### Smaller findings

- **F8.** `frontend/playwright.production.config.ts:15` uses `??=`, so an exported empty `E2E_DEMO_PASSWORD` reaches the server as `DEMO_PASSWORD=""` and `e2e:production` fails on startup. The 16.2 triage #12 changed only the public config to `||=`. Lens: edge-case. **Fix** (action item 6).
- **F9.** Several seed-skip warnings say "added on the next start":
  - `auth/__init__.py:168-170`
  - the category seed in `app/categories.py`
  - the bootstrap docstring
  The lifespan seeds only when `APP_ENV=local`, so in production a skip is not retried by a start, only by `swp db upgrade` or Demo version. Lens: adversarial. **Fix** (action item 6).
- **F10.** `backend/tests/test_deploy.py` does not pin `excludeFiles` (`vercel.json:13-15`, `{tests/**,var/**}`). Plan creation reads `backend/settings/analysis.toml` at runtime (`app/plans.py:23`). A future glob edit that drops `settings/` breaks New Plan on the public URL only. The author's SM-2 run on 2026-11-28 shows it works today. Lens: verification-gap. **Fix** (action item 6).
- **F11.** `184070b` suppresses every `OSError` on the default `backend/var` mkdir, not only `EROFS`, so a local permission or disk error surfaces later as an unclear SQLite error. Lens: adversarial. **Defer** (low).
- **F12.** `frontend/e2e/support/test.ts:140-147` retries a 429 five times at 500 ms intervals, about 2.5 s, which is shorter than the 60 s lock a slow start can leave. No flake has been observed since the 16.0 fix (453/0/0 in 16.1 and 16.2). Lens: adversarial. **Defer**.
- **F13.** The cached dummy hash (`auth/__init__.py:108-111`) makes the first unknown-name login on a cold Vercel instance cost an extra bcrypt `hashpw`. That is a timing signal for account existence. The deployment holds synthetic data only (NFR-5), and Create account already reveals taken names. Lens: adversarial. **Accept**.
- **F14.** The held-change verdict compares usernames (`frontend/lib/api/session-expiry.ts:205-210`). On the shared `demo` account, the next visitor counts as the "same user". The change is still recorded under `demo`, which is correct, because it is the same account. 16.0's purpose (no change saved under someone else's name) holds. Lens: adversarial. **Accept**.

### Process lessons

- **P1. A hardening story changed the next story's preconditions, and only the build of the next story found it.** 16.0 made `JWT_SECRET`/`DEMO_PASSWORD` mandatory in production. The 16.1 spec still followed `epics.md` and hit a blocker at implementation time (`spec-16-1` Implementation Notes). `184070b` (read-only `/var/task`) and `52a7fb5` (cold login over 5 s) were also found only on the live site. Lesson: when a story tightens a startup or runtime rule, re-read the ACs of the stories that depend on it before they start. For deploy stories, expect one live-fix commit and budget for it.
- **P2. Retro bookkeeping is split across two trackers and has drifted.** 37 action items are marked resolved in `.logs/justas/issues.md` (with commit or triage evidence) but still `open` in `sprint-status.yaml` (Previous-retro follow-through). The 2026-11-26 issue triage closed them in `issues.md` only. Lesson: whoever closes a retro point in `issues.md` also flips its `sprint-status.yaml` entry with `sprint_status.py update --set-action-status`.
- **P3. Live-fix commits carried no story id.** `184070b` and `52a7fb5` do not name 16.1/16.2 in the subject, so `git_evidence.py` attributes them to no story. Minor. Name the story in fix commits.
