### Diff-scope review (bmad-review)

**R1. Medium: after merging another tab's colours, the CSS variables no longer match the store's memory.**
- Where: `frontend/lib/colours/storage.ts:186-194` (`setKeyColour`), from commit `255680d`.
- What happens: `setKeyColour` builds `next = {...latest(), ...change}` and sets `values = next`, but calls `apply(change)` only. A colour another tab stored is now in `getKeyColours()` but not on `<html>`.
- Consequence for 11.3, which no single story saw: the popover's open-time colour and its warnings come from memory, not from what the wall shows. Esc, or Done with no change, calls `previewKeyColour(entry, null)` (`colour-popover.tsx:302-304`, `storage.ts:213-218`). That repaints the wall in the other tab's colour without notice.
- The 11.3 triage rejected "Esc restores from memory" on the premise that memory is what this tab had. The 11.2 two-tab merge broke that premise.
- Disposition: fix now (action item 1).

**R2. Medium: when storage can be read but not written, a second change drops the first one from memory.**
- Where: `storage.ts:119-127` (`latest()` falls back to memory only when `getItem` throws), with `:188`.
- What happens: with failing `setItem`, a change to B rebuilds memory from the stale stored JSON, so the unsaved change to A leaves `values`. A's variable still shows the new colour, but its popover opens on the old one, and Esc or an unchanged Done repaints it back.
- This weakens the 11.2 AC "the change still applies from memory for the page's life" in the read-works, write-fails case. The specs treat that case as rare, and the 11.2 and 11.3 triage rows on it concern only the note, not memory loss.
- Disposition: fix now (action item 1).

**R3. Medium (verification gap): no test can catch R1 or R2.**
- `tests/fr42_key_colours_storage.test.ts:244-251` (two tabs) checks only the stored JSON, never the `--colour-*` property against `getKeyColours()`.
- The blocked-write unit test (`:253-262`) and the e2e step (`e2e/key-colours.spec.ts:374-393`) each make a single change.
- Disposition: fix now, with R1 and R2 (action item 1).

**R4. Low (verification gap): the mapping from Key entry to colour is never pinned.**
- `components/common/wall/key.tsx:77-84` (`KEY_COLOUR_OF`).
- No test references it. The e2e test exercises only slow and best. Swapping fast and medium, or mapping `selected` to something other than `selection`, would pass every test.
- Disposition: fix now (action item 2).

**R5. Low: the three stories accept three different hex spellings.**
- `lib/colours/maths.ts:8,12` (11.1) trims the value and accepts it without `#`. `storage.ts:51` (11.2, the parser) requires `#` and does not trim. `colour-popover.tsx:60` (11.3, the field) requires `#`.
- So `setKeyColour("slow", " 378cbe")` succeeds, but the store's own reader would reject what it wrote back. No current caller passes such a value.
- Disposition: defer (action item 3).

**R6. Low: the store re-reads storage only when it writes.**
- `storage.ts:103-113`: `load()` caches for the life of the page, and there is no `storage` listener. "No live cross-tab repaint" is accepted in spec 11.2 and in `issues.md:192`.
- The new point is that the write-time merge is the only refresh path, which is what produces R1.
- Disposition: fold into action item 1 (either listen for `storage` events or drop the partial merge).

**R7. Low: a Done with no change can still repaint the wall.**
- `colour-popover.tsx:302-304`: this follows from R1 and R2.
- Disposition: goes away with action item 1.
